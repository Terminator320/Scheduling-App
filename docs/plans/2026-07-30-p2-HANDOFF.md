## 3. Bugs found while building — do not reintroduce these

All four were caught by tests, and three were defects in code I had just written. They are the
non-obvious failure modes in this area.

1. **`jumpToPage` inside `didUpdateWidget` crashes the framework** (`'!_dirty': is not true`).
   Changing the month from the picker or the Today pill mutates scroll state mid-build.
   `CalendarMonthPager` defers it to a post-frame callback that **re-reads `widget.month`** rather
   than capturing a target, so a burst of changes settles on the latest one. Never call
   `jumpToPage` synchronously from `didUpdateWidget`.
2. **A `PageView` echoes programmatic jumps back through `onPageChanged`.** `jumpToPage` fires it
   exactly like a swipe does, so a picker-driven month change round-tripped into `onMonthChanged`
   and reset the screen's focused day to the 1st of the month. `onPageChanged` now ignores a page
   that already matches `widget.month`. Keep that guard.
3. **The collapse re-arm direction is easy to get backwards.** "The expand arms once the user has
   scrolled past 44px" means the offset dropping **below** 44 on the way back up, not exceeding it.
   Reading it the other way makes a scroll-to-top never re-expand the grid. Arming and firing are
   also evaluated **in the same pass**, so a `jumpTo(0)` — which skips every intermediate frame —
   still re-expands. `collapse_state_test.dart` pins both.
4. **The ±14 overscan is asymmetric in origin, symmetric in value.** Max lead is 6 days (a month
   starting the day before the week start, e.g. August 2026); max trail is 14 (a 28-day February
   starting *on* the week start). February needs no lead at all. Two of my first test assertions
   were wrong because I assumed both extremes came from the same month.

## 4. Decisions taken, with the reason — do not "fix" them back

| # | Decision | Why |
| --- | --- | --- |
| 1 | **Off-month cells render a faint day number *and* their crew dots**, but stay untappable and out of the semantics tree | The design says "blank, Ink 15, not tappable"; the program spec widens the fetch to ±14 days *specifically* so trailing days are not dotless. Those only reconcile if the cells render dots. **Owner confirmed 2026-07-30 ("no blank").** |
| 2 | `visibleMonth` overscans **±14 days**, not ±7 | Exact cover for a 42-cell grid (see §3.4). Narrowing it silently empties trailing-cell dots. |
| 3 | The month grid **derives its own height** from the scaled day number; the `rowHeight` parameter is gone | The old clamp existed only because `table_calendar` demanded an explicit row height. Split panes now scroll instead of clipping at large text. |
| 4 | The split (`isSplitLayout`) pane keeps `SingleChildScrollView`, and **collapse is portrait-only** | The month\|agenda split has no room for a rising week strip, and it has two independent panes. |
| 5 | The three redundant `ColorScheme.light` arguments were **removed and replaced by a pinning test** (`test/core/theme/light_scheme_defaults_test.dart`) | Deleting them to satisfy the lint would leave the theme silently depending on Flutter defaults never changing. The test is a stronger guarantee than the arguments were. |
| 6 | The collapse spacer will be **derived** (`gridHeight − stripHeight`), not the design's literal 150px | Our grid is taller than the mock's and scales with text; 150 would visibly jump the list at the moment of collapse. Derived height makes the first card's position identical either side. **Not yet implemented — this is A5's job.** |

Decisions still to be made, all already argued in the plan: dropping `alwaysShowChip` (B1), the
crew bar following the *first* assignee (B1), losing the Cupertino branch on the repeat dialog
(C4), and the calendar having no `AppTopBar` (A4).

## 5. What A4 has to get right

The plan's Task A4 is accurate; these are the traps inside it.

- **`AppHeaderPair` works unchanged on a white surface.** It paints
  `scheme.primaryContainer`/`onPrimaryContainer` (blue tint on white), not app-bar colours, and it
  resolves its host via `Scaffold.of(context)` from anywhere in the body. No `GlobalKey` needed.
- **Dropping `Scaffold.appBar` means nothing sets the system overlay style.** The header must wrap
  itself in `AnnotatedRegion<SystemUiOverlayStyle>`, choosing light/dark icons from
  `ThemeData.estimateBrightnessForColor(scheme.surface)`. That is data-driven off the actual
  colour, so it does **not** violate the never-branch-on-brightness rule. Only the painted
  `IndexedStack` child contributes a layer, so the other three hub tabs' app bars are unaffected.
- **Keep the Day-route button wrapped in its `_tourStep(TourStepId.calendarDayRoute)`.** It is a
  feature-tour target; dropping it silently removes a step from the calendar tour.
- **`main_calendar_screen_test.dart` line ~103 asserts `find.text('Calendar')` finds 2 widgets** —
  the app-bar title plus the header pill. A4 removes the title, so that becomes 1. Update the
  assertion *and* its comment.
- **The 2× text-scale test at ~line 143 measures `find.byType(AppBar)`.** With no `AppBar` it will
  throw. Retarget it at the header block's own height.
- A4 also settles P1 handoff open decision 5 (the duplicate "Calendar") as a side effect.
