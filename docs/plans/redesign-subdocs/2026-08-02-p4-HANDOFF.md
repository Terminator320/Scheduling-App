## 2. Deviations — do NOT "fix" these back

| Deviation | Why |
| --- | --- |
| **No "time-to-leave alerts" toggle** (spec listed one in ACCESS) | The spec's own model table names no field to store it, and honouring it needs a user-doc flag *plus* a `travel_utils.js` change in `runTravelAwareReminderSweep` *plus* a functions deploy. Per-user notification toggles are P5's NOTIFICATIONS section. **Carried to P5 as an input.** |
| **Roster avatar is `AvatarSize.md` (36px), not the design's 40** | 40 falls between `md` (36) and `lg` (48). A fifth `AvatarSize` for one row would land a new size in a shared enum every list reads, and `md` is what the Clients roster already uses — matching the two rosters matters more than 4px. |
| **No COLOUR row in the info panel** | `KeyValueRow` carries a `String`, so a swatch cannot be a row without adding a `leading` slot to a shared widget for exactly one caller. The profile card's `AvatarSize.lg` avatar **is** the swatch, directly above the panel. |
| **TODAY renders "No jobs today" instead of omitting itself** | Single, deliberate exception to the omit-empty-sections rule. The panel answers "what is this person doing today?" and *nothing* is a real answer; omitting it is indistinguishable from the section not existing. Every other section still omits when empty. |
| **`EmployeeFormSheet` split into two sheets rather than extended** | Exactly P3's client split, for the same reason: after P4 the flows share four fields and diverge on everything else. One widget with `_isEdit` branching at eleven sites is how the client form became unmaintainable. |
| **No `ON CALL` info row** (approved-design graft 1) | On call is a chip beside the status chip in the profile card. A row would state the same boolean twice on one screen. `employees_onCallKey` was therefore never added. |
| **Working days are a `DAYS` phrase on the detail page, a grid only in the edit sheet** (graft 2) | The two surfaces want opposite things from the same data: the detail page is read, so the week wants to be a phrase taken in at a glance; the edit sheet is operated, so it wants seven tap targets. A read-only grid was an input-shaped control the reader cannot use, costing a whole section to say four words. |
| **Max jobs per day is a picker row, not a number field** (graft 3) | `SheetPanel`/`SheetFieldRow` are not text inputs. A `TextField` in a panel row looks tappable but wants a keyboard, and loses the error shake. A bounded numeric choice (No cap, 1–12) is a picker's natural shape. Emergency contact stays a `LabeledTextField` **below** the panel for the opposite reason — free text needs the shake and the clear button. |

## 3. Bugs and traps found while building

1. **The plan's own `formatWorkingDays` test would have failed.** Step 5 declared a second
   `monFirst` label constant for the weekend-worker case. `labels` is indexed by `storedIndex`,
   so it is **always** Sunday-indexed and never rotates — only `weekStart` changes per locale.
   `monFirst` would have produced `'Sun – Mon'`. The shipped test uses one Sunday-indexed const
   for both halves, which tests the adjacency quirk more directly.
2. **`FormSheetFrame`'s bar overflowed by 58px at 260×640 / 2.0 — pre-existing, not new.**
   Isolated with a throwaway probe: `FormSheetFrame(title: 'Edit client')` failed identically, so
   every P3 client sheet had been shipping it. Cancel and the primary verb were non-flex
   `TextButton`s, so the row had nothing to give once three intrinsic widths exceeded the
   viewport. Now all three slots are `Flexible` (3 / 4 / 3, side slots equal so the title stays
   optically centred) with `maxLines: 1` + ellipsis on both labels. **Shared-widget fix — it also
   fixes the client sheets.**
3. **`EmployeeFormSheet`'s edit path had to save via `copyWith`, not a fresh record.** Between
   Task 2 and Task 8 that sheet still handled edits but had no availability UI. Building a new
   record would have written `kDefaultWorkingDays` over real availability on every edit. Moot now
   the sheet is deleted, but the shape of the mistake generalises: **any partial form that saves
   a whole record must `copyWith` off the loaded one.**
4. **Both form sheets are lazy `ListView`s, so a phone-sized test viewport never builds their
   lower half.** `find.text('5')`, `'Dispatcher'` and the reassign caption all reported zero
   matches for widgets that render fine on a device. Their tests use a 900×3000
   `useTallViewport`; only the scale sweep runs at a real phone size.
5. **The rules deploy prints three warnings and that is correct.** `Unused function:
   isAvailabilityOnlyChange` plus two `Invalid variable name: request/resource`. Verified by
   temporarily adding a reference — all three vanished, then reverted. They are artifacts of the
   function being uncalled and go away when P5 wires it up.
6. **The invite sheet now seeds the first *unused* palette colour.** The old sheet always seeded
   `crewPalette[0]`, so a new invite defaulted to a colour someone already held unless the admin
   noticed. Adjacent to Task 3's bug and fixed with it.
7. **Seven tests targeted the disable affordance on a surface it left.** Task 6 removes
   Disable/Enable from the detail view; Task 7 adds it to the edit sheet — so the tests went red
   *between* the two commits. Handled inside Task 6: the two master-detail reconciliation tests
   were **retargeted** (they guard a real shipped regression, and now assert against the profile
   card's own status chip, which reads the rendered record rather than a control that depended on
   it); `employee_details_sheet_disable_test.dart` was deleted and its coverage re-created against
   `EditPersonSheet` in Task 7.

1. `users.name` is composed, never abandoned — `composeEmployeeName` can never return `''`.
2. `jobTitle` is not `role`; the chips have no side effect on the ACCESS toggle.

   takes unrotated Sunday-indexed labels.

   (`phone` is capped at the server's 40, not `TextLimits`' 32).
5. An employee is never deleted — disable is the only removal.
6. A disabled or invited employee's colour is TAKEN (`allUsersStreamProvider`, not
   `employeesStreamProvider`).
7. `isAvailabilityOnlyChange()` has no caller yet and must not be deleted as dead rules code.
8. (Conventions) The roster's jobs-today count is ONE listener reduced in Dart, keyed off
   `currentDayProvider`.

## 7. Deploy — ordering hazard, do not skip

`functions/invites.js` and `firestore.rules` both changed. `firestore.indexes.json` did **not** —
`countFutureAssignments` is served by the existing `(employeeIds CONTAINS, startTime ASC)`
composite index.

```bash
cd functions && npm run lint && npm test && cd ..
firebase deploy --only functions,firestore:rules,storage
```

**Never pass `--force`** — it deletes any prod Firestore TTL policy missing from
`firestore.indexes.json` (that removed all five live policies once, 2026-07-21). Omit
`firestore:indexes`. `storage` is the correct target, not `storage:rules`.

**The hazard:** the Dart client now sends `firstName`, `lastName`, `jobTitle` and `isAdmin` to
`createEmployeeInvite`, and the **live** callable's `assertPayloadShape` allowlist does not
include them — and `assertPayloadShape` **rejects unexpected keys**. So from the moment a build
containing Task 2 ships, *every invite fails* against the un-deployed function.

> **Deploy `functions` before shipping a build containing Task 2, or ship both together.**

`allow delete` on `/users` is withdrawn at the same deploy. Between the code change and the
deploy the rule is still open, but nothing in the app calls it.
